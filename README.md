# DealFlow SQL

A production-shaped analytics warehouse for a commercial property deal pipeline, built on
PostgreSQL 16: **1.54 million raw rows** landed from four deliberately messy source feeds,
loaded through staging and an intermediate layer into a star schema of **1,165,043 fact
rows across 85 partitions**, **248,940 deals**, and two Slowly Changing Dimension
Type 2 dimensions carrying **14,651 versions**. Every row is gated by **12 in-pipeline data
quality rules** and **51 standing assertions**, and the whole thing rebuilds from an empty
database in **about 7 and a half minutes** with one command.

> **All data is synthetic.** It is generated by [`generate_data.py`](generate_data.py) from
> the fixed seed `dealflow-2026-v1`, which stands in for four source systems and injects 19
> named defect classes on purpose. No real broker, agency, property, deal or client appears
> anywhere in this repository, and every email domain is `.example`.

## Reproduce the whole thing

```bash
./run.sh
```

Docker is the only prerequisite. That single command creates the container, builds seven
schemas, generates and loads 1.54 million raw rows, runs both loaders, builds the star,
runs the quality gates, and executes the 14 analysis queries. **Measured end to end: 6m 52s,
7m 08s and 7m 42s** on three full rebuilds of an 8 vCPU laptop container.

**Running it twice is safe, and that was checked rather than assumed.** Every row count in all
31 tables across the six schemas was compared before and after a second full run. Twenty-nine
came back byte identical. The two that moved are `dq.assertion_run` and `dq.assertion_result`,
and they moved *down*, because `01_staging.sql` drops and recreates the `dq` schema so the
append-only assertion history restarts at run 1. That is the rebuild doing what it says, not a
loss of idempotence: the quality gate then re-observed the same findings it observed the first
time. The generator is deterministic and every write is idempotent, so the anomaly loop
converged in the same two passes both times.

```bash
./run.sh --scale 0.05   # the same pipeline on 5% of the volume, for a fast smoke test
./run.sh quality        # 51 data quality assertions
./run.sh benchmark      # the 6 performance case studies
./run.sh psql           # a SQL shell on the warehouse
```

Query output rendered as a browsable page: [`results.html`](results.html), regenerated from
live query results by `./run.sh results`.

## What this demonstrates

| Technique | Where | The problem it solves |
|---|---|---|
| **SCD Type 2 from a full snapshot** | [`03_load.sql`](sql/03_load.sql) step 7 | A full snapshot tells you state, never change. Hash-compare over the tracked attributes finds version boundaries in one window pass. A broker who moved agency in 2023 must still report their 2022 deals under the old agency. |
| **SCD Type 2 from a delta feed** | [`03_load.sql`](sql/03_load.sql) step 8 | Identical code, opposite source shape. A delta feed cannot be trusted to contain only real changes, so a `RECLASSIFY` row that changed nothing tracked must not open a version. The hash is what proves it did not. |
| **Overlap exclusion as the real guarantee** | [`02_warehouse.sql`](sql/02_warehouse.sql) section 3 | `EXCLUDE USING gist (broker_nk WITH =, tstzrange(valid_from, valid_to) WITH &&)`. One constraint enforces two invariants: no two versions of a key overlap, and therefore exactly one is current. The database enforces it, not a careful loader. |
| **Generated column kills a whole defect class** | [`02_warehouse.sql`](sql/02_warehouse.sql) | `is_current GENERATED ALWAYS AS (valid_to = 'infinity') STORED`. The most common Type 2 defect in production is `is_current` drifting out of step with the window after a manual backfill. This makes it unreachable rather than unlikely. |
| **Declarative range partitioning** | [`02_warehouse.sql`](sql/02_warehouse.sql) section 4 | 84 monthly partitions plus a DEFAULT, created by a function so the load can make a month it has never seen at 3am without a human editing DDL. Pruning takes case 1 from 85 partitions in the plan to 3. |
| **Extended statistics, per partition** | [`fn_ensure_month_partition`](sql/02_warehouse.sql) | `from_stage_sk` and `to_stage_sk` are near functionally dependent, so the planner multiplies independent selectivities and underestimates every funnel query. Measured: the object on the **parent** changed nothing; on the **child** it corrected an estimate of 96 to exactly 924 against an actual 924. |
| **BRIN where it belongs, and only there** | [`01_staging.sql`](sql/01_staging.sql), [`PERFORMANCE.md`](PERFORMANCE.md#case-5-brin-measured-and-then-rejected) | 24 kB against 25 MB for the equivalent btree on the landing table, and the planner chose it. On the partitioned fact it was built, measured and **deleted**: a free query rewrite beat it by a further 5x to 7x across three runs. |
| **Partial and covering indexes** | [`02_warehouse.sql`](sql/02_warehouse.sql) | The open-pipeline index tracks the working set instead of growing with history: 728 kB against 12 MB. `INCLUDE` on the returned columns gives `Heap Fetches: 0`, an index-only scan. |
| **`MERGE` for idempotent upsert** | [`03_load.sql`](sql/03_load.sql), [`04_facts.sql`](sql/04_facts.sql) | Four staging tables and the snapshot fact are `MERGE`d on their source key, so a retried load updates instead of duplicating. Verified: re-running both loaders leaves every row count byte identical. |
| **A cache key that is actually the source** | [`06_performance.sql`](sql/06_performance.sql) preflight block `010_fixture_provenance` | The benchmark fixture takes 68 s to build and 3 s to verify, so it is cached. It used to cache on `broker_sk`, a surrogate key assigned by an identity sequence, and a warehouse rebuild that renumbered it made a second benchmark run die on the SCD2 exclusion constraint. Now the fixture records a checksum of every warehouse column it copied and rebuilds when that moves. **Three consecutive runs, no manual reset, all clean.** |
| **Window functions that earn their place** | [`03_load.sql`](sql/03_load.sql) step 10, [`05_analytics.sql`](sql/05_analytics.sql) | `LAG` derives `from_stage` and dwell once at load time instead of every report re-running a window over 1.1M rows. `ROWS` vs `RANGE` frames are contrasted on the same series (Q04), and gaps-and-islands finds unbroken activity runs (Q12). |
| **Recursive CTE over a real hierarchy** | [`05_analytics.sql`](sql/05_analytics.sql) Q13 | A three-level agency group rolled up with cycle detection, producing `Agency 002 > Agency 028 > Agency 060` paths and each node's share of its group. |
| **Error-tolerant loading that reconciles** | [`03_load.sql`](sql/03_load.sql) steps 2, 3 | One unparseable value must not cost the other 262,499 rows their load. Bad rows are diverted with a reason code and the original text, and **DQ-001 proves nothing was lost**: raw offered equals staged plus rejected plus quarantined, exactly. |
| **Quality rules as data** | [`01_staging.sql`](sql/01_staging.sql), [`fn_run_dq_gate`](sql/02_warehouse.sql) | 12 rules live in a table with their SQL, threshold band and the generator defect each exists to catch. One runner executes all of them, records every observation, **then** raises. Recording before raising is deliberate: a gate that aborts on the first failure hides the other eleven. |
| **A standing assertion suite** | [`07_quality.sql`](sql/07_quality.sql), [`run_quality.py`](run_quality.py) | 51 assertions in two batteries. The **warehouse** battery is our correctness contract and all 30 pass. The **staging** battery is a supplier scorecard and reports 18 findings, which is its job. |
| **Point-in-time key resolution, proved** | [`03_load.sql`](sql/03_load.sql), DQ-005 | A foreign key proves a key exists. Only DQ-005 proves it was the version **in force when the event happened**, across all 1,165,043 fact rows. That is the one thing about a Type 2 dimension no constraint can check. |
| **Watermarks and a run log** | [`meta`](sql/01_staging.sql), [`04_facts.sql`](sql/04_facts.sql) step 6 | Watermarks start at `-infinity`, so the first load and every nightly delta take the same code path and there is no bootstrap script to drift. They advance **only after the final gate passes**, so a failed run reprocesses rather than skipping data forever. |
| **Convergent anomaly removal** | [`03_load.sql`](sql/03_load.sql) step 10c | Removing a bad event changes the `from_stage` of the next one, which can create a new anomaly. Written as one pass with an assertion, the assertion **failed at 1,219 rows**, so it became a fixed-point loop. It converges in 2 passes: 8,155 then 1,139. |
| **Deterministic synthetic data** | [`generate_data.py`](generate_data.py), [`fn_u`](sql/01_staging.sql) | `setseed()` plus `random()` is not reproducible under a parallel plan, because every worker seeds its own generator. Measured: two identical runs gave checksums `896e96ec...` and `7761a4e1...`. A hash of the row's own key gives the same draw regardless of plan shape. |

## Performance

**Six case studies, every number measured, worst outcome reported alongside the best.**
Full write-up with plans and buffer counts: **[PERFORMANCE.md](PERFORMANCE.md)**.

Ranges are across **five runs of the suite**, each the median of 5 timed runs after one warmup.
The bolded figure is the *lowest* speedup observed on any run, because that is the one worth
quoting.

| Case | Fix | Before | After | Speedup, 5 runs |
|---|---|---:|---:|---:|
| 1 | Rewrite `to_char(ts,'YYYY-MM')` as a half-open range on the partition key | 220 to 412 ms | 12 to 52 ms | **~8x** to 24x |
| 2 | Composite index leading with the equality column | 61 to 116 ms | 3.1 to 6.5 ms | **~13x** to 23x |
| 3 | Ordered index feeds the window, eliminating a 48 MB disk sort | 5.8 to 8.4 s | 3.5 to 6.2 s | **~1.3x** to 1.7x |
| 4 | Partial index plus `INCLUDE`, giving an index-only scan | 21 to 62 ms | 4.9 to 8.6 ms | **~3.4x** to 9.7x |
| 5b | Query rewrite beats the BRIN index it was compared against | 16 to 33 ms | 3.2 to 5.6 ms | **~4x** to 9.1x |

**The plan facts are what reproduce, and they reproduce exactly.** Case 1: **85 partitions in
the plan down to 3**, buffers 21,220 read to 1,098 hit, identical on every run. Case 4:
**33,965 buffers down to 202** with `Heap Fetches: 0`, byte identical every run. Case 3: temp
blocks written **20,713 down to 8,706**, byte identical every run. Over those same runs the
case 1 wall clock speedup moved between 7.7x and 24x. That gap is the reason this table quotes
ranges and minimums, and why [PERFORMANCE.md](PERFORMANCE.md) leads with the buffer evidence
rather than the milliseconds.

Case 3 is in the table because it is the one that **mostly did not work**. The plan win is
unambiguous (temp blocks written fall from 20,713 to 8,706) and the clock win is marginal,
because `percentile_cont` must sort its whole input and no index can change that. On one of
four suite runs it measured net slower. The real fix for that question is the materialized
aggregate, not an index.

## Design decisions and trade-offs

**Why a star schema and not one wide table.** The pipeline is asked two structurally
different kinds of question: "how many deals moved from Qualified to Offer last quarter, and
how long did they sit" and "how long does a deal take from receipt to offer, by cohort".
The first needs one row per transition; the second needs one row per deal. A single wide
table can serve one of them well and the other badly. So there are two facts at two grains,
sharing conformed dimensions: the event fact is the **immutable audit trail** and is only
ever appended to, and the snapshot fact is **current truth** and is overwritten in place,
with every overwrite logged to `dq.restatement_log`. Denormalising further would also break
Type 2: agency attributes on a broker row would mean rewriting every historical broker
version whenever one agency is reclassified, which is exactly the rewrite Type 2 exists to
avoid.

**Why Type 2 on broker and property, and Type 1 on agency.** A report about the past has to
describe the past. A broker who moved from Agency 012 to Agency 041 in March 2023 still
closed their 2022 deals under Agency 012, and a property rezoned from Industrial to Mixed
use must still report a 2021 deal as Industrial. Those are the two attributes this business
slices by, so they are versioned. Not every column on those tables is: `full_name`, `email`
and `phone` are Type 1 and deliberately **excluded from `row_hash`**, because a corrected
spelling is not a new version of a person and hashing it would open a spurious version for
every typo fix. `dim_agency` is Type 1 outright because it is an outrigger with its own
change cadence and 61 rows, and versioning it would multiply versions on the 1,207-row
dimension that points at it for no reporting gain.

**Why partition on `event_date` and not on `received_date`.** The reporting grain is
month-over-month funnel, so a month is the unit analysts filter on and pruning hits on
almost every real query. `received_date` was the tempting alternative and it is wrong for
two reasons. First, an event's date is the thing queries range over; a deal's receipt date
is a dimension of the deal, not of the event. Second, partitioning the **snapshot** fact by
`received_date` was tried and rejected on a correctness argument, not a performance one:
PostgreSQL requires the partition key in every unique index, so `PRIMARY KEY (deal_nk)`
becomes illegal and the enforced grain silently becomes `(deal_nk, received_date)`. That was
proved on the live database, by restating one deal's `received_date` and re-running the
`MERGE`: it **inserted a second row**, leaving the same deal alive in two partitions.
Date restatement is a defect this project deliberately seeds, so that is not hypothetical.
Unpartitioned at 248,940 rows and a 53 MB heap, `PRIMARY KEY (deal_nk)` enforces the true
grain and a restatement updates in place.

**Why monthly and not daily.** Daily would be about 2,900 partitions. The planner must
consider every partition before it can prune, and that cost was measured on this data at up
to 21 ms when no pruning applies against 0.2 ms when it does. Quoting the cost and not only
the win is what makes this a decision rather than a fashion.

**Why these indexes and no others.** Every index in `02_warehouse.sql` carries a
`QUERY SERVED` comment naming the access path it exists for, and after the query suite runs,
`benchmark.py` reads `pg_stat_user_indexes` and writes
[`plans/index_usage.txt`](plans/index_usage.txt) so an unused index is visible rather than
assumed. The column orders are not arbitrary: `(broker_sk, event_date)` puts the equality
column first because a composite btree can only use a range predicate on the column after
the last equality. Two indexes are partial because their queries only ever look at a subset
(open deals, terminal events) and a partial index on a table that accumulates forever tracks
the working set instead of growing with history. There is **no BRIN on the fact**, and that
absence is measured rather than assumed: see
[PERFORMANCE.md case 5](PERFORMANCE.md#case-5-brin-measured-and-then-rejected).

**Where the dedupe is knowingly imperfect.** Resubmissions arrive with a fresh message id, a
later timestamp and a value jittered by up to 2 percent, so no identifier can find them. The
blocking key is `(conformed broker, conformed property, ISO week)`. The value is
deliberately **not** in the key: the first version bucketed it to the nearest R100,000 and
caught only 4,588 of about 9,600 resubmissions, because the jitter is proportional and the
bucket was absolute. Blocking has a structural blind spot, and this repository measures it
rather than hiding it: when the defect lands **on the blocking key itself**, the pair splits
across two blocks and both survive. That is 238 deals, 0.096 percent, and `ASSERT-WH-014`
bands it at 400 so a regression is caught. The fix is priced in that assertion's comment:
multi-pass blocking plus transitive clustering, which is the right design where 0.1 percent
matters and over-engineering where it does not.

**What I would do differently at 100x the volume** (116 million fact rows, 25 million deals):

- **Move the sort-heavy transforms off `work_mem` guesswork.** Case 3 already spills 28 MB
  at 1x. At 100x, `LAG` over the whole event history stops being a single statement. It
  would become a per-partition transform driven off the partition registry, so the window
  runs inside one month at a time and never sorts more than it has to.
- **Partition weekly or keep monthly but detach aggressively.** 84 partitions is fine and
  8,400 is not. At 100x I would keep monthly partitions and use `DETACH CONCURRENTLY` plus
  a rollup into `mv_broker_month` beyond a rolling 36 months, which is what
  `meta.partition_registry` and its `detached_at` column already exist to support. The
  aggregate keeps answering the historical questions; the fact stops carrying pages nobody
  reads.
- **Stop `TRUNCATE`-and-rebuild in `int`.** Rebuilding 1.1 million intermediate rows every
  run is cheap and honest at 1x, and it is 116 million rows of pointless work at 100x. The
  watermark infrastructure is already there; `int` would become incremental too, keyed on
  the affected deals rather than all of them, exactly as
  `util.fn_sequence_stage_events(run_id, deals)` already does for the anomaly loop.
- **Replace `DISTINCT ON` dedupe with the multi-pass blocking described above.** At 25
  million deals, 0.1 percent is 25,000 deals, which is no longer a rounding error.
- **Reconsider the accumulating snapshot's `MERGE`.** Updating in place is right at 249,000
  rows. At 25 million, a nightly full `MERGE` rewrites a large fraction of the heap and
  generates the WAL to match. I would key the `MERGE` off the deals that actually had an
  event in the batch, which the watermark already identifies.
- **What I would not change:** the layer boundaries, the reject-and-reconcile contract, the
  `EXCLUDE` constraint, the generated `is_current`, or the rules-as-data gate. Those get
  more valuable as volume grows, not less, because they are the things that make a 3am
  failure diagnosable.

## Honest limits

- The volume is 1.16 million fact rows, not a billion. Everything here is *shaped* like
  production; nothing here has survived production.
- Timings come from a Docker container on a laptop. Magnitudes are stable across runs, exact
  figures move by 20 to 40 percent, and the harness prints min / median / max and flags
  competing backends so a reader can see it.
- The staging battery reports 18 findings by design, because the generator seeds 19 defect
  classes on purpose. The **warehouse** battery is the one that must be clean, and it is:
  30 of 30.
- Fixed-date South African public holidays only in `dim_date`. Easter and the observed-Monday
  rollover are out of scope and stated as an assumption rather than left to be discovered.
