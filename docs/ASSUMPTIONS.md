# Assumptions and reporting conventions

Every convention the analytics layer relies on, in one place, so that a number
in a report can be traced back to the rule that produced it.

> **All data is synthetic.** It is generated by [`generate_data.py`](../generate_data.py)
> from the fixed seed `dealflow-2026-v1`. No real broker, agency, property, deal
> or client appears anywhere in this repository.

## Reporting timezone

The reporting timezone is **Africa/Johannesburg**, pinned on the database itself
by `sql/01_staging.sql` step 0 rather than described in prose:

```sql
ALTER DATABASE <current> SET timezone = 'Africa/Johannesburg';
```

Pinning it on the database rather than in a README is the point. Every session,
every cron job and every BI tool that connects inherits it, so `event_ts::date`
means the same thing everywhere. A convention that lives only in documentation is
a convention that one connection string can quietly break.

**What that buys, concretely.** `mart.fct_deal_stage_event.event_date` is derived
from `event_ts` under this timezone, and the partition key is `event_date`. So the
month-boundary rewrite in `sql/06_performance.sql` case 5b (filtering `event_date`
instead of `event_ts`) is only equivalent because the two agree under a pinned
zone. Under an unpinned zone they select different rows at the boundary.

**The honest limit.** On this dataset the boundary is never exercised. Measured:

| Check | Result |
| --- | --- |
| Events between 00:00 and 01:59 JHB | 0 |
| Earliest event hour (JHB) | 06 |
| Rows where `event_date <> (event_ts AT TIME ZONE 'Africa/Johannesburg')::date` | 0 |
| Rows where `event_date <> (event_ts AT TIME ZONE 'UTC')::date` | 0 |

JHB is UTC+2 with no daylight saving, so a UTC reading and a JHB reading can only
disagree for events between 00:00 and 01:59 JHB. The generator never emits one.
The design is therefore **correct by construction, not proven correct by this
data**. It would start mattering the moment a real feed carried an overnight
batch, which is exactly when nobody would be looking.

## Grain

Two facts, and mixing them is how a funnel dashboard starts lying:

| Fact | Grain | Use it for |
| --- | --- | --- |
| `mart.fct_deal_pipeline` | one row per deal | deal counts, win rates, open book value |
| `mart.fct_deal_stage_event` | one row per stage transition | funnel steps, dwell time, event volumes |

Every query in `sql/05_analytics.sql` states which grain it works at. Where a
ratio needs both, the numerator and denominator are drawn from the same
population (see Q08, which previously did not and reported 100 percent for six of
seven stages as a result).

The two do not reconcile exactly, on purpose:

| Population | Count |
| --- | --- |
| Deals in `fct_deal_pipeline` | 248,940 |
| Deals with any stage event | 248,702 |
| Deals with a `Received` event | 248,189 |

So Q01 reports 248,940 received deals and Q02's funnel base is 248,189. The 751
difference is deals whose `Received` event was quarantined upstream or never
arrived. Q02 says so in its header rather than letting a reader find two intake
totals on one page and assume one of them is wrong.

## The warehouse horizon

Named partitions on `mart.fct_deal_stage_event` run from 2020-01 to 2026-12, plus
a `DEFAULT` partition (`sql/04_facts.sql`). **`DATE '2027-01-01'` is the
horizon.**

The generator deliberately injects out-of-range dates so that the data quality
layer has something real to catch. `ASSERT-STG-018` and `DQ-012` both flag them.
They still land in the fact, in the `DEFAULT` partition, where they are visible
rather than silently dropped:

| Bad data | Count |
| --- | --- |
| Events dated 2027 or later (all 2031) | 369 |
| Won deals with a `closed_won_ts` in 2031 | 25 |

**Being flagged upstream is not the same as being safe downstream.** Two reports
had to be bounded explicitly:

- **Q04** would have published "the top broker closed R16.81m in September 2031".
- **Q08** pinned its "as at" date to `max(event_date)` over the whole fact, which
  returned **2031-12-30**. Every "days silent" figure was inflated by about 1,978
  days, the minimum silence across the open book came out at 143 days, that
  exceeds twice the largest SLA, and so every stage reported exactly 100 percent
  at risk. Bounding `as_at` to the horizon returns the report to 24.5 percent
  through 80.2 percent, which is a report a manager can act on.

Any query that reads a max date, or that publishes a date to a human, bounds
itself to the horizon and says so in a comment.

## Money

- All monetary output is South African Rand.
- Stored measures are `numeric(18,2)` in whole Rand. Never a float: binary
  floating point cannot represent 0.10 exactly, and a warehouse that sums money
  in `double precision` will disagree with the finance system by cents that
  compound.
- Columns suffixed `_zar_m` are divided by 1e6 and `_zar_bn` by 1e9, purely for
  legibility in a terminal.
- `deal_value_zar` is nullable. 2,907 of 248,940 deals (1.168 percent) carry
  NULL, which is why `DESC NULLS LAST` is mandatory on any window that ranks by
  value. See Q04 and Q10.

## "As at" dates

Pinned to the last event in the warehouse, never to `now()` or `CURRENT_DATE`, so
a query re-run next month returns the same answer and a committed output file
stays reproducible. Bounded to the horizon, per the section above.

## Dimension keys

- **`broker_sk` on a fact is a VERSION key, not a person key.** `mart.dim_broker`
  is Type 2: 1,207 versions across 801 current brokers. The loader resolves the
  version that was in force on the day of the event.
- To ask a question about a **person**, hop twice: join the fact to the historic
  version on `broker_sk`, then back out through `broker_nk` to the row where
  `is_current`. Q05, Q12 and Q14 all do this.
- Filtering `WHERE b.broker_sk = <literal> AND b.is_current` is **not** a filter,
  it is an inner join that deletes every row attributed to a superseded version.
  49,049 of 248,940 pipeline rows (19.7 percent) carry a non-current
  `broker_sk`.
- **Unknown members** sit at negative surrogate keys (`broker_sk = -1`,
  `agency_sk = -1`) and are `is_current`. Any report that names human beings
  excludes them explicitly (`> 0`). Any report measuring data quality includes
  them on purpose.

## Cohorts are left-censored

`Q11` assigns a broker's cohort from their first deal **inside the warehouse
window**, which opens 2020-01-01. Every broker already working before that date
lands in 2020-Q1: 753 of 1,132, or 66.5 percent. 25 of the 26 cohorts hold fewer
than 30 brokers and the smallest holds 8. Only the 2020-Q1 row is large enough to
read as a trend. Fixing this needs a broker start date from the source system,
which this warehouse does not receive.
