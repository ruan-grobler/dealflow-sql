# Defects found in this repository, and what each one taught

Every defect below was found in **my own code**, on this dataset, and fixed here. This file
exists because a codebase with no visible failures is less believable than one with a list of
them, and because the mechanism of a bug is usually more interesting than the feature it
broke.

Format for each entry: **what I saw**, **what I first assumed** (usually wrong, which is the
useful part), **what was actually happening**, and **what changed**.

> All data is synthetic, generated by [`generate_data.py`](../generate_data.py) from the fixed
> seed `dealflow-2026-v1`.

## 1. The dedupe key that caught less than half the duplicates

**What I saw.** The suppression count came out at 4,588 against an expected population of
about 9,600. The assertion band caught it.

**What I first assumed.** That the resubmission generator was under-producing, so I went
looking at the generator rather than at the key.

**What was actually happening.** Resubmissions arrive with a fresh message id, a fresh deal
reference, a later timestamp and a deal value jittered by up to 2 percent. My key was broker
plus property plus **the value bucketed to the nearest R100,000** plus the ISO week. The
jitter is **proportional** and the bucket was **absolute**: 2 percent of a R30 million deal is
R600,000, six buckets wide, so the pair never landed in the same bucket. A relative bucket does
not fix it either, it just moves the failure to the bucket boundaries, which the jitter
straddles.

**What changed.** The value came out of the key entirely and became **evidence**. The key is now
a blocking key (broker, property, ISO week) and the value delta is recorded in the suppression
log for audit. Recall went to 9,622, a 3.7 percent rate, inside the expected band. **A key has
to be exact; evidence does not.**

**What it still gets wrong, measured.** In 349 of 9,597 blocks the paired values differ by more
than 5 percent, so some suppressions may be genuinely distinct deals. And blocking has a
structural blind spot: when the defect lands **on the blocking key itself**, the two rows fall
into different blocks and both survive. That is 238 deals, just under 0.1 percent, and they show
up as deals in the snapshot fact with no event history at all.

## 2. The single-pass anomaly removal that my own assertion caught

**What I saw.** Nothing. The code looked right and the counts looked plausible.

**What I first assumed.** That every physically impossible event is the **last** event of its
deal, so removing it cannot affect anything else, so one pass is enough. That reasoning is
almost right, which is the dangerous kind.

**What was actually happening.** I did not trust the reasoning, so I wrote an assertion to check
it rather than to confirm it. **The assertion failed at 1,219 rows.** A second, independent
defect was interacting with the first: a mistyped year throws an event to 2031, so it sorts
*after* its deal's real terminal event, which makes the transition into it come out of a
terminal stage. Removing an anomaly in the middle of a stream then changes the `from_stage` of
the event after it, which can create a brand new anomaly that was invisible on the first pass.

**What changed.** A fixed-point loop that re-derives only the affected deals and repeats until
nothing changes. It converges in two passes on this data, 8,155 events then 1,139. There is a
hard iteration cap that raises a clear error rather than spinning, because each pass must remove
at least one event, and if that argument ever stops holding I want the load to fail in seconds.

**The lesson.** This is the difference between a pipeline that is correct and one that happens
to be correct on the data the author looked at. Write the assertion to **check** the assumption,
not to confirm it.

## 3. `DESC` defaults to `NULLS FIRST`

**What I saw.** Q04 returned **one row** instead of 77.

**What I first assumed.** A broken join or an over-tight filter. I went looking at the `WHERE`
clause.

**What was actually happening.** The top-broker subquery was `ORDER BY sum(...) DESC LIMIT 1`.
In PostgreSQL `DESC` implies `NULLS FIRST`, so a broker whose only won deal carried a NULL value
sorted **above** the real top earner and won the `LIMIT 1`. The report then had one broker with
one month of history. It looked *empty* rather than *wrong*, which is exactly why it survived
review.

**What changed.** `NULLS LAST` on the ordering, and a comment stating the default so the next
person does not have to rediscover it.

**And then it happened again, which is why this entry matters.** Q10, a concentration-risk
report written later in the same file, shipped with the identical bug. See defect 10.

## 4. Assertions that asserted calendar invariants against the DEFAULT partition

**What I saw.** Three warehouse assertions failing on a build that was otherwise clean.

**What I first assumed.** That the calendar dimension was wrong.

**What was actually happening.** The DEFAULT partition exists precisely to hold dates no
calendar will ever have. Asserting "every fact date exists in `dim_date`" across the whole fact
therefore asserts something the design deliberately violates.

**What changed.** The assertions were scoped to the declared partition range, shared through one
view (`mart.v_fact_declared_range`) so the scope is defined once rather than pasted three times.
The out-of-range rows are still counted, by `DQ-012`, which bands them 1 to 8,000 rather than
asserting zero.

## 5. A quarantine key that could not express a verbatim redelivery

**What I saw.** `DQ-001`, the reconciliation that proves nothing was lost, did not reconcile
exactly.

**What I first assumed.** An off-by-one in the reject counting.

**What was actually happening.** `dq.quarantine_stage_event` was keyed on `event_nk`. A verbatim
redelivery is **two raw rows carrying one event id**, so the second one could not be recorded
without colliding with the first, and the row vanished from the arithmetic.

**What changed.** Rekeyed on the **raw row address** (file plus line), which is unique by
construction. `DQ-001` now reconciles to zero: raw offered equals staged plus rejected plus
quarantined, on both large feeds.

## 6. `NOT VALID` is refused on a partitioned parent

**What I saw.** The standard low-lock pattern for adding a foreign key to a large table,
`ADD CONSTRAINT ... NOT VALID` followed by `VALIDATE CONSTRAINT`, failed outright.

**What I first assumed.** A syntax error on my side.

**What was actually happening.** PostgreSQL 16 does not support it on a partitioned table:

```
ERROR:  cannot add NOT VALID foreign key on partitioned table "fct_deal_stage_event"
        referencing relation "dim_property"
DETAIL:  This feature is not yet supported on partitioned tables.
```

**What changed.** Nothing in the schema, and that is the finding. I measured the plain
validating `ADD CONSTRAINT` on the parent instead and it is cheap enough at this volume that the
per-partition workaround buys a shorter lock on each of 85 tables in exchange for 85 DDL
statements and no constraint on the parent. The measurement, and the caveat that the cost grows
with row count, are in PERFORMANCE.md.

## 7. The benchmark that could not be run twice

**What I saw.** A second run of `benchmark.py` against an already-populated lab schema died:

```
ERROR:  conflicting key value violates exclusion constraint "ex_dim_broker_no_overlap"
```

**What I first assumed.** That the fixture builder was simply missing an idempotence guard. It
was not. It had one.

**What was actually happening.** The guard was keyed on the wrong thing. It asked *"is this
broker version already loaded?"* by comparing `broker_sk`, a surrogate key the lab does not own:
`sql/03_load.sql` assigns it from an identity sequence with no `ORDER BY`, so rebuilding the
warehouse can hand the same brokers different numbers. The guard then saw keys it did not
recognise and re-inserted versions it already held. **The constraint that fired was keyed on
`(broker_nk, validity window)`. The guard was keyed on a number that had moved.**

The drift is intermittent, not guaranteed, which is why this survived: one warehouse rebuild
during the work happened to reassign identical keys and the bug did not reproduce. It was
isolated by injecting exactly that renumbering into a throwaway schema.

**What changed, and what was rejected.** Not `ON CONFLICT DO NOTHING`: an untargeted one does
swallow exclusion violations, and it would have left the lab holding rows keyed to the old
numbers while every fact resolved against the new ones, so the suite would have gone on
reporting speedups measured against the wrong rows. **Trading a loud crash for a silent wrong
measurement is the worst trade available in a benchmark.** Not an unconditional rebuild either:
building is 68 s and verifying is about 3 s, so verifying is roughly 20x cheaper, and forcing a
rebuild would make the single-case flag cost a minute a time.

Instead the cache key was fixed. A new preflight block stores a checksum of every warehouse
column the lab copies, written **only after** the fixture verifies itself, so its presence means
"a complete fixture built from this exact warehouse". The guard now matches on
`(broker_nk, valid_from)`, the grain the constraint protects.

**The lesson.** An idempotence check has to be keyed on the same thing the constraint is keyed
on, or the constraint is what tells you the check was wrong.

**Applied where it had not bitten yet.** Three sibling fixture blocks assigned surrogates with a
bare `ROW_NUMBER()` behind a guard. `ROW_NUMBER()` restarts at 1 whenever the guard filters
anything out, which is the same failure shape. All three now offset from the existing maximum
and match on the natural key.

## 8. The benchmark that measured ten months and called it a career

**What I saw.** Case study 2's headline: *"114 rows out of 1,165,043, 0.0098 percent"*, under a
question that reads *"for one broker, across their whole history"*.

**What I first assumed.** That the selectivity was just very good, and it made the case
dramatic. I quoted it in two documents.

**What was actually happening.** `WHERE e.broker_sk = 407`. On a Type 2 dimension `broker_sk` is
a **version** key, not a person key. 407 is one **closed** version of broker `BRK-000270`, valid
from `-infinity` to 2020-11-01, and that broker has a second version still open. The query held
114 of that broker's **948** events and returned a single row, for the year 2020. The
selectivity that made the case dramatic was an artifact of having picked a ten-month stub rather
than a person.

**How it was found.** By asking what the number meant. 114 events for a whole career is
implausible, so counting the broker's events by natural key gave 948, and the gap was the
question.

**What changed.** The filter resolves **every version of one natural key**, which is the honest
form of the question and still has no access path without the index the case adds. And the
broker is no longer hardcoded: it is resolved at fixture build time to *"the lowest numbered
broker with more than one version"* and recorded in `perf.fixture_provenance`, because an
identity-assigned surrogate moves when the warehouse is rebuilt, which is the exact fragility
defect 7 exists to catch.

## 9. `is_current` on a fact join is not a filter, it is a deletion

**What I saw.** Nothing. The leaderboard looked fine.

**What I first assumed.** That `JOIN dim_broker b ON b.broker_sk = f.broker_sk AND b.is_current`
pinned the report to today's org chart, which is what the comment above it claimed.

**What was actually happening.** `f.broker_sk` is the point-in-time resolved **version** key, so
adding `AND b.is_current` turns the join into an inner join that **drops every deal attributed
to a superseded version**. Measured: 49,049 of 248,940 pipeline rows carry a non-current
`broker_sk`. On the current-year leaderboard that silently removed 772 deals. Worse,
`pct_of_total_won_value` is a `sum() OVER ()` evaluated **after** the join, so every published
share was a share of an already truncated book.

**What changed.** The two-hop pattern that `Q14` already used and this file had failed to apply
to its neighbours: join the historic version by surrogate, then join back out through
`broker_nk` to the current row. That genuinely does pin attributes to today's org chart without
throwing history away. Applied in `Q05` and `Q12`, cross-referenced in both.

**The uncomfortable part.** The repository's own thesis is Type 2 dimensions, `Q14` explains the
correct pattern in a comment, and two queries in the same file did it wrong anyway.

## 10. The same `NULLS FIRST` bug, in the report where it matters most

**What I saw.** `largest_single_broker_pct` was NULL for seven of nine sectors, and
`top3_share_pct` for three. NULLs are visible, so that part looked like a data-quality question
rather than a bug.

**What I first assumed.** That some sectors genuinely had no priced open deals.

**What was actually happening.** Q10's window was `ORDER BY o.open_value_zar DESC,
o.broker_sk` with no `NULLS LAST`, which is precisely the defect Q04 documents six hundred lines
above it. 2,907 of 248,940 deals (1.168 percent) carry a NULL `deal_value_zar`, producing 16
(sector, broker) groups whose open value summed to NULL, and those sorted to `broker_rank` 1.

**The part that was worse than NULL.** `top5_share_pct` was not NULL for a single sector, it was
**silently understated for every one of them**, because ranks 1 through 4 were placeholders
contributing nothing to the cumulative sum and by rank 5 a real broker had finally entered it.
Retail published 5.18 percent against a true 14.18. Industrial 10.96 against 16.95. Healthcare
13.09 against 18.26. A concentration report that understates the top-5 share by nine points is
worse than no report, because it reads as a plausible number. I reproduced the broken form
against the current warehouse to get those figures rather than quoting them from memory.

**What changed.** `NULLS LAST` on the window, plus `COALESCE(sum(...), 0)` on the aggregate so a
broker with no priced deals ranks at zero rather than at NULL and cannot poison the cumulative
window either. Both cross-referenced to Q04 so the two read as one policy.

## 11. Invented band labels on the two buckets that have no bounds

**What I saw.** A histogram with clean half-decade band labels, and a comment asserting that no
deal fell outside the chosen bounds.

**What I first assumed.** The comment. It said the bounds were *"chosen from the measured range
(log10 min 4.70, log10 max 9.33)"*.

**What was actually happening.** The measured range is log10 **2.52** (R328.82) to **9.61**
(R4.12 billion). 603 deals fell in bucket 0 and 3 in bucket 11. `WIDTH_BUCKET` returns 0 for
below-range and n+1 for at-or-above-range, and **both of those buckets are unbounded on one
side**, so a band label computed arithmetically from the bucket number is a fabrication for
them. Bucket 0 was printed as "R10,000 to R31,623" while actually holding deals from R328.82,
so the printed lower edge excluded most of its own contents.

**What changed.** Bounds widened to 2.5 through 10.0 in 15 buckets so the data sits inside them,
the parenthetical corrected to the measured values, and the band labels **still** guarded with a
`CASE` that returns NULL for an unbounded edge, so a future load that moves the range gets an
honest NULL rather than an invented number.

## 12. The index usage check that was aimed at the wrong schema

**What I saw.** `plans/index_usage.txt`, presented in the README as proof that every index in
the warehouse had earned its place. It listed no findings.

**What I first assumed.** That there were none.

**What was actually happening.** The query filtered `WHERE s.schemaname = 'perf'`. That is the
benchmark lab. The artifact contained **not one warehouse index**. The tool reported nothing
because it was pointed at the wrong target.

**What it found when aimed at `mart`.** Three indexes with zero scans after a full load and the
entire analytics suite: `ix_fct_event_terminal` (0 scans, 14 MB across 85 partitions, three
paragraphs of justification I wrote myself), `ix_dim_broker_agency` (0 scans), and
`uq_dim_broker_current` (0 scans).

**What changed.** Two deleted, one reclassified. `ix_fct_event_terminal` was designed for the
query I imagined rather than the one I wrote: a partial index only helps a query that repeats
its partial predicate, and neither `Q09` nor `Q02` filters on `is_terminal_event`.
`uq_dim_broker_current` stayed, because a unique index is a **constraint** and a constraint is
judged on whether the invariant is wanted, not on scan count. Its comment, which claimed to be
an access path for the loader, was rewritten to say so. The artifact now covers `perf` and
`mart`, and states that PK and unique-constraint indexes are exempt from the zero-scan rule.

## 13. Known-bad data walking into a business report

**What I saw.** Q04's rolling-average demonstration had exactly one row where its two window
frames disagreed, which is the divergence the whole query exists to show. And Q08 reported
**every** stage at exactly 100 percent at risk.

**What I first assumed.** For Q04, that the series was sparse, which is what the comment claimed.
For Q08, that the open book really was that stale.

**What was actually happening.** Both were the seeded 2031 dates. The generator injects
deliberately out-of-range close dates, `ASSERT-STG-018` and `DQ-012` both flag them, and
`04_facts.sql` parks them in the DEFAULT partition on purpose. But nothing stopped them reaching
the **reports**. Q04's one divergent row was `2031-09`, telling a manager the top broker closed
R16.81m five years in the future. Q08 pinned "as at" to `max(event_date)` over the whole fact,
which is 2031-12-30, so every silence figure was inflated by about 1,978 days, the minimum
silence across the open book came out at 143 days, that exceeds twice the largest SLA, and the
report flagged 100 percent of everything, which tells a manager nothing.

**What changed.** Both queries bounded to the same warehouse horizon the partition range
enforces. Q08's stages now separate cleanly, 24.5 percent of the Due diligence book at risk
against 80.2 percent of Triaged. Q04's comment was rewritten to say honestly that on this data
the two frames agree everywhere, rather than claiming a sparsity the data does not have.

**The lesson.** A data-quality problem being correctly flagged upstream does not stop it walking
into a business answer downstream. Flagging and excluding are two different jobs.

## 14. Two grains, one ratio

**What I saw.** In Q08, `pct_of_stage_open_book` read exactly 100.0 for every stage except
Received, which read 85.4. An oddly specific exception.

**What I first assumed.** Rounding.

**What was actually happening.** The numerator counted open deals by their last event, from the
**event** fact. The denominator counted `mart.fct_deal_pipeline WHERE is_open AND
current_stage_sk = ...`, from the **deal** fact. 238 open deals exist in the pipeline fact with
no rows at all in the event fact (they are the blind spot from defect 1), and they all sit in
Received. The file's own header warns that mixing the two grains is how a funnel dashboard
starts lying, and then the file did it.

**What changed.** Both sides counted from the same CTE, so the ratio is a share of the population
it is drawn from.

## 15. The flagship BRIN ratio, measured on the wrong table

**What I saw.** *"BRIN is about 1,060x smaller than the equivalent btree"*, used in the README as
the reason all four landing tables carry BRIN.

**What I first assumed.** That it was a measurement of the landing table. It was labelled as one.

**What was actually happening.** It was measured on `perf.raw_stage_event`, the benchmark
mirror, whose `ingested_at` is populated from the **event** timestamp: 1,152,758 distinct values
over 1,165,043 rows, near-unique, which is precisely the case where a btree is largest. The real
landing table `raw.stage_event` has **79 distinct `ingested_at` values over 1,204,742 rows**,
because a batch ingest stamps a whole file at once. btree deduplication collapses repeated keys
into posting lists, so the real btree is **8,200 kB**, not 25 MB.

**What changed.** Both numbers are now published, labelled by table. The honest ratio on the
table the decision actually governs is **342x**. The decision it justifies was correct either
way, which is what made leaving it unstated worse rather than better: nobody would have caught
it, and it would have come apart in one follow-up question about what a real ingest timestamp
looks like.

## 16. The password that was in `ps(1)`, under a comment saying it was not

**What I saw.** `run.sh` line 52: *"never printed, never passed on a command line where ps(1)
could read it"*. Three lines below it, `docker run -e POSTGRES_PASSWORD="$POSTGRES_PASSWORD"`.

**What I first assumed.** That `-e VAR=value` was the only way to pass an environment variable
to `docker`.

**What was actually happening.** `-e VAR=value` puts the literal value in `argv`, where any local
user running `ps` can read it, for the whole life of the process. A benchmark run is minutes of
continuous exposure. Reproduced with a canary value: `ps -Ao args` printed it. `-e VAR`, the
name-only form, does not, because docker reads the value from the calling process's environment.
`generate_data.py` and `build_results.py` already did it the safe way, so the two files that got
it wrong were inconsistent with the rest of the repository as well as with their own comments.

**What changed.** Name-only form in `run.sh` and `benchmark.py`, and the comment rewritten to
stay true, including the part it had been leaving out: the value is still readable via
`docker inspect`, which is a local-container trade-off and not a secret store.

## 17. A column that held the wrong thing and nothing noticed

**What I saw.** Nothing at all. Nothing queried the column.

**What was actually happening.** `perf.dim_date.iso_week` was populated with
`EXTRACT(ISODOW FROM d)`, which is ISO **day of week** (1 to 7), under a heading that says
**week** (1 to 53). `2026-03-15` read 7 where the real ISO week is 11. `mart.dim_date` was
correct, and the fixture's own header claimed it "mirrors the mart definitions".

**What changed.** The extract corrected, and, more usefully, the word *mirror* is now **checked
rather than asserted**: the fixture verification block compares `perf.dim_date` against
`mart.dim_date` column by column and fails the build if they disagree on any row. A claim in a
comment is not a test.

## 18. A rollup query that threw its own answer away

**What I saw.** Q13, whose stated question is *"what does each entire group contribute once every
subsidiary beneath it is counted"*, produced output that stopped part-way into the third
alphabetically named group.

**What was actually happening.** `ORDER BY root_agency_name` with `LIMIT 25`, over a tree of 60
nodes across 20 root groups. The recursive CTE, the cycle guard and the carried-down root were
all correct. The presentation discarded 18 of the 20 answers.

**What changed.** The `LIMIT` is gone (60 rows is a screen, not a data dump) and the `ORDER BY`
now leads with the group total, so the top of the output is the answer to the business question
rather than the alphabetically first agency.
